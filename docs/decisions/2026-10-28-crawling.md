# Crawling with Crawlee and confined handlers

Status: proposed acquisition architecture; Cheerio endowment implemented in this
branch, together with container-backed bridge roles, but not released. Runtime and
transport spikes are validated; production crawler integration is not built.

Use Crawlee as the acquisition engine and Pronto's existing compute seat for
application parsing. Compute modules declare the `Cheerio` endowment and may call
app-owned Crawlee-shaped functions from their ordinary `finish` function. The
application neither imports platform confinement internals nor runs its own cage.
A native Rust transport preserves SofaScore's browser-like TLS and HTTP/2 behavior,
which succeeded where Impit received HTTP 403.

Pronto owns durable request scheduling, source ownership, validation, and canonical
updates. Airlock submits individual acquisition work to crawler workers. Responses
return as append-only CRUD intents; change processing invokes compute. No polling
protocol or callback endpoint on Airlock is required. The acquisition service is an
application-owned container hatch exposed through a bridge role. Its parsing worker
is Jessie on compute; Crawlee and the native helper run in the acquisition container.

The legacy tools are [[../../tools/crawl_championship.py]],
[[../../tools/crawl_players.py]], [[../../tools/crawl_teams.py]],

consistent database snapshot and transactional import rather than web acquisition.

## Ownership and event flow

1. A schedule, user intent or completed parse creates durable request intents with
   stable identities, a crawl generation, source, transport profile and input data.
2. The scheduler determines eligibility and commits a worker assignment/lease.
   That transaction enters the invoking state and claims an Airlock submission.
   The crawler durably accepts that assignment before answering; repeated submission
   with the same assignment key finds the same work.
3. Airlock records successful submission. This means accepted, not fetched. Crawlee
   manages bounded execution, connections and source pacing on the assigned worker.
4. The worker appends the raw response and transport metadata through authenticated
   CRUD. It retains unacknowledged output and repeats delivery with the same ID.
5. Change processing invokes the ordinary compute module. Its pure parsing produces
   normalized observations and further request intents. The ingestion transaction
   validates these outputs and durably records them before marking parsing complete.
6. Application machines derive crawl completion from persisted requests, responses
   and parse outcomes. Deadline events handle abandoned work; there is no status poll.

Early responses remain processable even if Airlock has not recorded acceptance yet.
A superseded assignment cannot complete a newer attempt. Every response retains its
request, assignment and crawl-generation identities. A response from a stale worker
may be retained as evidence, but cannot overwrite the authoritative completion.

The Airlock ledger records submission of a bounded acquisition unit. It does not
prove that exactly one HTTP request reached the source: an ambiguous failure may
require repeating a read. Native redirects and any bounded transport retries need
attempt metadata. Individual fetch observability requires individual work records,
not merely putting a whole crawl behind one Airlock invocation.

The bridge role supplies internal routing, startup dependencies and outbound network
placement. It neither defines the container twice nor confines its application code.
It does not change callback semantics or put application parsing inside the bridge.
Airlock's private ledger remains its own; workers submit ordinary response intents,
not fabricated Airlock outcomes. See
[[../../../../libraries/mecha/services/airlock/README|Airlock's contract]].

## Why parsing and scheduling stay in Pronto

The alternative is a crawler that owns the complete request graph, application
callbacks and intermediate state, with only job acceptance and completion visible
to Pronto. That is efficient for tight browser sessions and deep high-volume crawls,
but moves application recovery and debugging into another runtime.

The primary benefit of the chosen indirection is debugging through replay. Persist
the source response, request metadata, parser version and explicit contextual inputs.
When a parser mishandles a score or a team name, reproduce the failure on that input,
change the parser, and compare new observations without contacting the source again.
Keep raw observations immutable; reparsing creates a new derivation/version, and
promotion into canonical facts still obeys ownership and review rules. A replay must
not automatically redispatch historical follow-up requests: suppress acquisition for
analysis-only replay, or explicitly promote deduplicated request intents.

Missing requests, malformed responses and partial matches are inspectable persisted
states. The same input and parser version can be exercised in the same compute seat
used in production. Captured bytes, deterministic code and context are required;
Jessie alone does not reproduce a changed upstream page or undeclared business state.

The cost is extra commits and hops between discovery steps, raw-response retention,
and explicit joins between related responses. For Golaberto's shallow JSON graph and
paced legacy crawl this is a reasonable trade. Larger bounded external operations
remain possible where measurements or browser session affinity justify them.

## Multiple workers and centralized scheduling

Crawlee supports parallel workers consuming a request queue with locking. Its
ordinary local storage is not a distributed scheduler merely because it persists
files. A shared backend must implement the coordination semantics; local process
concurrency and durable cross-machine ownership are separate concerns. See
[Crawlee parallel scraping](https://crawlee.dev/js/docs/guides/parallel-scraping),
[request storage](https://crawlee.dev/js/docs/guides/request-storage), and
[RequestQueue](https://crawlee.dev/js/api/core/class/RequestQueue).

Pronto can own the centralized scheduler while Crawlee owns each worker's bounded
execution. Feldera is a good proposed fit for incrementally deriving eligible work
from pending requests, dependencies, worker capabilities/capacity, source cooldowns,
and active assignments. This scheduler has not been implemented or load-tested.

Eligibility is not a claim. A transactional machine/SQL operation must revalidate
availability, reserve the request and shared source budget, and create an assignment
with a lease and fencing generation. Concurrent candidates cannot each consume the
same final capacity slot. Persist assignments and dispatch them through Airlock;
do not dispatch directly from transient eligibility rows that may retract or replay.

Workers report acceptance, responses, failures and renewal intents through the same
authorized ingress. Lease expiry and cooldown changes are explicit clock events so
time can advance eligibility even when no other data changes. Exhausted leases make
work eligible again; fencing prevents a late worker from settling its replacement.
Bound retries and distinguish retryable acquisition failure from deterministic parse
failure, which should be reparsed or reviewed rather than blindly refetched.

Use one authority for durable work ownership. Do not combine Pronto assignments with
an independent shared Crawlee queue that can reassign the same work. Local Crawlee
queues may buffer assigned work; they do not define global completion. Global
per-source concurrency and rate budgets must remain global when workers scale out;
multiplying a local per-worker limit is not a source-wide limit. Session-bound work
needs affinity to a worker or an explicit external session service.

## Configuration and application code

Use supported Crawlee options for concurrency, pacing, request limits and handlers.
The acquisition worker must admit a data-only configuration subset. Its fixed
transport implementation consumes those options; application parsing is supplied
through declared compute modules. Arbitrary launcher objects, plugin constructors
and host callbacks are not configuration capabilities. This admission layer remains
application implementation work.

An app-owned function can keep the familiar Crawlee shape:

```js
export async function requestHandler({ json, request, $, addRequests, pushData }) {
  const rows = json.data.map(row => {
    const cell = $.load(row[0]);
    return { name: cell('a').text(), href: cell('a').attr('href') };
  });
  await pushData(rows);
}
```

The compute module receives explicit input snapshots and constructs `json`, the
supported plain-data fields of `request`, and `Cheerio.load(html)` for its helper.
`addRequests` and `pushData` collect proposed requests and records locally. No host
queue or database write happens until the handler succeeds and the host validates
its entire output. These methods acknowledge collection, not durable delivery.
Dataset selection and request options outside the supported contract are refused.
This is a supported API subset with explicit commit semantics, not arbitrary
Crawlee-plugin compatibility.

The compute/application boundary checks output shape, strict JSON representability, size, request counts,
source destinations and allowed methods. It must reject unsupported values rather
than silently coerce them through JSON serialization. Follow-up intents and collected
output need an atomic durable checkpoint before parsing is marked complete;
a crash must not lose follow-up work or assign fresh delivery IDs to replayed output.

Business decisions depending on existing records or time receive explicit input
snapshots and instants. Canonical identity matching, manual-edit ownership and
source precedence remain application ingestion rules, not hidden database access
from a scraper. Pair SofaScore lineups and incidents by event and crawl generation
before applying a combined observation.

## Cheerio and confinement

The existing compute seat gives each computation a fresh worker with no Deno permissions. The worker uses
Pronto's [[../../../../libraries/mecha/services/compute/realm.ts|locked realm]] and
[[../../../../libraries/mecha/services/compute/compartment.ts|compartment]], with
[[../../../../libraries/mecha/services/compute/workers.ts|the existing module compiler]].
The application's single computation module has no imports or ambient host capabilities.
The existing compute runner closes the worker after a settled run but does not
enforce a deadline on a nonterminating parser. Host-enforced timeout/termination and
parser resource bounds are required before unattended acquisition is deployed. The
historical spike has a deadline; that guarantee is not yet in the compute seat.

Declare `endowments: ["Cheerio"]` and call `Cheerio.load(html)`, retaining its
standard traversal, callbacks, mutation, serialization, and fragment parsing APIs.
The document is mutable private scratch state, so do not recursively harden `$` or
its DOM. Freeze ordinary input data and the context's outer shape separately. A
fresh worker prevents modified parser prototypes or documents from affecting later
invocations. Never share that worker with privileged transport or credentials.

Do not endow the entire top-level Cheerio module. Cheerio 1.2.0 exposes `fromURL`
and stream loaders there; acquisition must remain in the host. Its `cheerio/slim`
entry point supplies the ordinary document API using htmlparser2 without importing
the network loaders. This parser choice differs from the default parse5 behavior;
representative malformed legacy HTML needs fixture coverage before migration.

Compatibility and targeted escape tests passed for Cheerio 1.0.0-rc.12 and the
1.2.0 slim entry point. These tests are not a blanket security certification or a
static Jessie-language proof. Dependency pinning, worker isolation, output
validation and resource bounds remain part of the contract. A wall-clock timeout
alone does not bound memory consumed by parsing or output construction.

## Transports

Transport selection names a fixed profile implemented by the application-owned
acquisition service, never a shell command supplied by a parsing handler. Ordinary HTTP uses the selected standard client. SofaScore uses the
upstream helper's wreq Chrome 149/macOS profile and its fixed request headers.
Build the helper with a pinned Rust toolchain and lockfile into the service image.
The Deno adapter invokes a fixed executable with argument arrays, never a shell.

The spike connects it through Crawlee's `BaseHttpClient` interface. Its success-only
CLI drops status, headers and redirect metadata, so the spike buffers the body and
synthesizes HTTP 200 JSON metadata. That is sufficient to demonstrate the integration,
but is not the production transport contract.

Before implementation is accepted, add a structured protocol carrying status,
headers, final URL, redirect history and bounded body data, with typed transport
errors. Preserve allowed-source checks on every redirect. Enforce response-size
limits while reading, and ensure cancellation kills and reaps the native process.
A native helper must not be assumed constrained by Deno's network permissions:
its own destination policy and deployment egress restrictions carry that boundary.
Validate scheme, hostname, port and credentials, and address resolution if the
policy excludes private destinations.

The initial transport is a fixed-header, direct GET profile. Cookies, proxy pools,
header overrides and arbitrary methods are not silently accepted. Either implement
and test those capabilities explicitly or refuse their configuration. A persistent
helper can later reuse connections, but must preserve per-request cancellation and
response correlation; process-per-request is the validated starting point.

## Response inbox and resilience

Give the crawler a dedicated identity permitted to append to the response-intent
inbox, with tenant/source row policies as required. It cannot update or delete
responses, read unrelated tables, write canonical facts, or use `SERVICE_JWT`.

Each response identifies the job generation, source request, stable delivery ID,
handler version, response kind and payload. Ingress suppresses identical delivery
retries; conflicting payloads under one delivery ID must be rejected or quarantined.
A completion record carries a manifest or count of expected batches so processing
can determine completeness without assuming delivery order. Pending, rejected and
superseded observations remain distinguishable from successfully applied ones.

The inbox is durable application input, consumed through changes rather than a
polling/claiming queue. Retention must respect processing checkpoints and any raw
response replay policy. A raw-response artifact reference needs its own authenticated
retrieval and lifetime contract; it is not automatically available to consumers.

Use bounded acquisition concurrency and output buffering. Resilience for local,
Kubernetes and GCP ingress is a separate platform change: investigate circuit
breaking on the CRUD path without automatically enabling write retries. Client
errors must not trip a shared circuit for unrelated callers. The crawler still owns
durable pending delivery when ingress is unavailable. Cloudflare free tier is an
intentionally limited target and need not provide equivalent resilience.

## Deployment boundaries

The acquisition image is portable across Linux container hosts, but hosting an image
and deploying the full Pronto pipeline are separate requirements. No target currently
ships the completed Golaberto crawler. Resilience is deferred independently of these
execution and packaging gaps.

| Release model | Current boundary |
| --- | --- |
| Local Compose | Existing compute and Airlock seats plus the new container-bridge wiring; Golaberto must implement its worker, ledger, callback permissions and computations |
| `release@docker` appliance | Packages a smaller core stack; the acquisition and compute/Airlock pipeline are not included |
| Kubernetes | Can host the image, but current release manifests do not package the complete required pipeline |
| GCP Cloud Run target | Its release engine rejects compute, Airlock, transform and clock services; GKE would follow the Kubernetes path |
| Cloudflare | Compute/transform deployment and acquisition integration are absent; native acquisition needs a separate host |

Start with local Compose. Kubernetes and GCP need release packaging work in addition
to application implementation. For the edge app, scheduling, authenticated ingress
and derived-data refresh against Worker/PGlite must be wired and tested separately.
The existing Docker updater does not establish any of those edge integrations.

macOS ARM64 and Linux ARM64 native helper builds and live requests passed. Windows,
x86_64, and the complete Deno service on Linux need their own validation. A WASM
recompile is not the deployment strategy: the current networking stack rejects the
plain wasm target, and delegating to host fetch would lose the TLS profile.

Playwright is a future transport/runtime capability. No existing crawl requires it;
exposing its browser objects to a handler requires a separate capability review.
CAPTCHA providers and proxy pools likewise stay outside the initial contract.

## Golaberto implementation handoff

This branch adds `Cheerio` to the platform's declared cage endowments, packages the
pinned slim parser into compute and Airlock images, and tests an ordinary computation
calling an app-owned Crawlee-shaped function. The normal `reads`, `queries`, `plan`
and `finish` contract is unchanged. See
[[../../../../plugins/pronto/docs/pipelines-and-schedules|the computation guide]].

Golaberto must consume a platform release containing that support; the previously
pinned public Mecha v0.17.0 does not provide the new endowment. Once released, the
application does not need private platform code or internal cage imports. The old
relative imports remain only in the historical architecture spike.

| Work | Owner |
| --- | --- |
| Cheerio endowment, parser pin and image packaging | Platform change in this branch; release required |
| Crawlee-shaped parsing helper inside normal compute module | Golaberto; no new platform handler contract |
| Native transport, worker service/image, job protocol | Golaberto initially |
| Request/response entities, parser outputs, ownership and ingestion | Golaberto |
| Central eligibility computation and atomic assignment machines | Golaberto using existing primitives; validate before scaling |
| Container-backed bridge role | Platform change in this branch; release required |
| Crawler container hatch and its bridge declaration | Golaberto |
| Shared CRUD circuit breaking and full edge execution integration | Deferred platform/deployment work |

The bridge role references an ordinary container hatch: `state.bridges.crawler`
names its `container` and HTTP `port`, and an effect selects `sink.bridge: "crawler"`.
The application owns the image, command, resource limits and callback credential.
Pronto wires the internal endpoint and startup dependency; Mecha attaches its
outbound networks without implicitly attaching the database network. Mail uses the
same mechanism through a reusable SMTP container recipe. See
[[../../../../plugins/pronto/docs/container-bridges|container bridges]].

The crawler is declared once as a `container` hatch and supplied through
`cluster.surface.targets.crawler`. The bridge only references it:

```cue
code: capabilities: hatches: crawler: {
    kind: "container"
    note: "Crawlee acquisition with native TLS; responses return through restricted CRUD"
}
code: state: bridges: crawler: {container: "crawler", port: 8080}
```

Effects select `sink.bridge: "crawler"`. Missing or non-container hatch references
and missing container build definitions fail compilation. The role supplies no
callback token or database permission; those remain explicit application capabilities.

This deployment role does not confer confinement on Crawlee, exactly-once acquisition,
or database permissions. Jessie parsing, the crawl ledger and response replay remain
separate application concerns. The bridge accepts work promptly and sends results
through CRUD; it does not keep the Airlock call open until a crawl finishes.

The handoff is not turnkey app code. Begin with individual SofaScore requests,
response persistence, parsing/replay and response intents on the container target;
then migrate archive HTML handlers. Keep the application API familiar while proving
the durable acceptance, checkpointing and transport requirements below.

## Evidence and implementation gates

Reproduction commands and logs live in
[[../../../../experiments/crawlee-deno/index|the isolated spike]].

- Deno 2.5.4, Crawlee 3.18.2, Impit 0.14.7: fixture JSON graph succeeds; live
  SofaScore returns 403 with legacy and default headers.
- Native helper: the same events URL succeeds on macOS; round 1, lineups and
  incidents also succeed. The integrated Crawlee plus confined-handler run emits
  26 events, two 23-player lineups and 24 incidents as three summary records.
- The platform compute tests exercise declared Cheerio and an app-owned
  Crawlee-shaped function called by ordinary `finish`.
- Compiler and cluster tests cover generic container bridges, custom ports, invalid
  references and absence of implicit database-network attachment. The generated
  Compose stack delivers SMTP through the reusable mail container and verifies
  network isolation, ledger behavior and the mail process's declared permissions.
- Thirty-two confinement/HTML tests cover both Cheerio versions, real legacy HTML and
  HTML-in-JSON fixtures, representative authority escapes and worker isolation.
- Five adapter tests cover destination rejection, cancellation, subprocess cleanup
  and nonzero exits. Seven upstream helper tests cover headers, allowed URLs,
  redirects, error previews and stalled response timeout; they pass on both tested OSes.
- Linux ARM64 container builds from a digest-pinned Rust image and fetches 26 live
  events. Linux end-to-end Deno execution remains an implementation gate.

Implementation acceptance must additionally prove job acceptance/restart recovery,
atomic handler-output checkpointing, replay-safe response delivery, append-only
identity enforcement, early and stale callbacks, completion after reordered batches,
structured transport metadata, enforced byte limits, and canonical updates that do
not rewrite unchanged derived facts. The spike deliberately does not implement
Airlock submission, CRUD authentication, CDC ingestion or production scheduling.
