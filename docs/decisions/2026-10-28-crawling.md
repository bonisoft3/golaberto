# Crawling with a native transport and database parsing

Status: built for SofaScore on the local stack; no release target lowers the
transport yet. Container-backed bridge roles, the `Cheerio` compute endowment and
database functions are built. Requests, observations, the newest-answer view,
receipt, scheduling, failures, enrollment and identity recovery are SQL
(`services/database/sql/059_sofascore_requests.sql`); parsing and reconciliation
are the `sofascore_normalize` and `sofascore_reconcile` functions. The request
machine claims the `acquire` effect through the `sofascore` bridge, which the local
stack runs as its simulator (`simulators/sofascore`). On release targets the effect
settles as not deployed. The Python coordinator is retired; the operations guide is
[[../sofascore-sync]].

Pronto owns scheduling, source ownership, parsing, validation and canonical updates.
The only native component is a stateless transport container: it performs one HTTP
GET with SofaScore's browser-like TLS and HTTP/2 profile and answers the response.
An Airlock effect calls it through a bridge. The commit that records the answer also
parses it with a fuel-bounded Jessie function and applies it when it is the newest
answer for its resource.

The transport cannot be replaced. SofaScore answers HTTP 403 to Impit and ordinary
clients; the native Rust helper's wreq Chrome profile succeeds. That networking stack
does not compile to plain WASM, and delegating to a host `fetch` loses the TLS
profile, so every target, Cloudflare included, needs a native container host.

## Domain rules

The SofaScore rules come from the first updater in
[#2171](https://github.com/worldsense/trash/pull/2171) and its tests, which a live
Italy pilot exercised. They carry over unchanged; only their runtime moves from a
Python coordinator into Pronto machines, functions and SQL:

- Cadence by distance to kickoff, round summaries serving all their matches, result
  summaries ahead of inventory and detail work, and the end-of-season audit period.
- Provider identities bound explicitly to existing teams, players and games; one
  confirmed binding per pair; duplicates and conflicts quarantined, never resolved
  by row order or fuzzy names.
- Baselines that protect editor changes, dates and kickoff times that follow the
  provider, live scores never recorded as final, and reviews for uncertain data.
- Verified stage bindings and composite cup-stage keys; an activation cutoff so
  enrollment never backfills historical details.

## Machines and flow

| Piece | Kind | Owns | Carries |
| --- | --- | --- | --- |
| `sofa.tick` | SQL, called by the `sofascore-admission` drain | Retention, sources past their season, stuck requests, fixture seeds, admission by priority within the budget | Nothing persistent |
| `sofa_resource` | Mecha reducer, one instance per resource | Its phase, next due instant, backoff, detail checks, settling and season audit | Ids and small facts; its state's timer, on the ticker, fires at its due instant |
| `sofa_provider` | Mecha reducer, one instance | The provider's standing: open, paused by 401/403 until resumed, blocked by 429 until its instant | Statuses and instants |
| `sofa.resource` | rows | Each resource's key, family, path and meta | Nothing the schedule decides |
| `sofa_request` | row machine | The Airlock claim and the commit that stores, parses and applies | The URL and kind; the raw response on its observation row |
| `fn_sofascore_normalize`, `fn_sofascore_reconcile` | [[../../../../plugins/pronto/docs/decisions/2026-11-05-database-jessie#Functions|database functions]] | Parsing, event patches and paired details patches: the first updater's `normalize.py`, response checks, `event_patch` and `details_patch`, ported | Nothing persistent |
| `sofa.current` | [[../../../../plugins/pronto/docs/decisions/2026-09-29-cortex-machines|DuckStream view]] | The newest observation per resource; a PostgreSQL view until the view tier lowers its declaration | Derived, not stored |
| `sofa.apply_source_patch` | SQL | Ownership, baselines and canonical writes | The patch |

1. When a resource or provider seat changes, a fixture changes, a day tick lands or a rate-limited budget window reopens, `sofa.tick` admits the resources whose reducers are `due`, while
   the provider is open and the budget lasts, each as a `sofa_request` row with
   the next sequence number of its source, which is the version the answer is
   asked about, and tells the reducer it was admitted. When `minute_limit` is
   exhausted with `due` resources still waiting, `sofa.admit` writes a one-shot
   `sofascore-budget` row to `public.schedule` for the next minute boundary.
2. The request enters `acquiring`, whose transition claims the `acquire` effect.
   Airlock's handler calls the transport bridge and returns the response.
3. `onDone` calls `sofa.receive`, which in one commit stores the observation and,
   when it is `sofa.current`'s row for its resource, parses and reconciles it,
   applies each patch and tells the resource's reducer what the answer owed: the
   fixtures still unsettled, whether the pair completed, the cache's max-age and
   the season's end. The reducer decides when it is next due, or that it is done
   or given up. The calendar day and detail eligibility read zones or the clock,
   so SQL computes them around the functions. A round inventory creates its
   rounds; a played final the source may detail creates its lineups and
   incidents; the detail that completes a pair applies both.
4. `onError` calls `sofa.fail`, which tells the reducer the status and Retry-After
   instant; the reducer backs off or, for a detail past five failures, gives up to
   review, and a 401, 403 or 429 is told to the provider's reducer.

Ids the functions cannot know are `{derive: parts}`, which SQL turns into the same
uuid for the same parts (`sofa.derive_ids`), so a redelivered detail rewrites the
same rows.
A fixture new to the source carries no local id out of the functions: the apply
step creates the game with a database-generated id and records its `sofa.binding`
in the same commit, and the binding's uniqueness makes every later delivery of that
event find the same game.

The effect declares `reentry: "repeat"`: an answer lost after the source replied is
fetched again, which a GET tolerates. The transport answers within Airlock's
60-second no-answer bound, so acceptance and completion are the same event: there
are no callbacks, delivery identities or completion manifests to reconcile.

## Late answers

Which answer is current is a function of the observations, not of when they arrive.
`sofa.current` selects, per resource, the observation with the greatest sequence
number. A sequence number is assigned in the admitting commit, so it orders
requests by when they were asked without reading a clock. A delayed or redriven
answer to an older request is stored and never becomes current, so it is never
applied. The provider's own change timestamps are data the parser may record; no
decision reads them.

`apply_patch` keeps the application's merge policy: which fields the provider owns,
editor baselines and reviews. It receives only current observations.

## Failures and dead letters

A function that throws, runs out of fuel or produces a patch `apply_patch` refuses
fails the `onDone` commit. Airlock has already committed the outcome, so the response
is kept in its ledger. The move is retried and, under
[[../../../../libraries/mecha/docs/decisions/2026-11-05-bounded-dead-letters|bounded dead letters]],
parked as a dead letter once its deliveries run out. A fix ships with a redrive, and
the stored response is parsed without refetching.

While a key is a dead letter:

| Part | Consequence |
| --- | --- |
| That resource | Shows its last applied data: stale, never partially written |
| Other requests and sources | Unaffected: each ledger key is delivered on its own |
| The request row | Stays in `acquiring` until redriven |
| Admission | Spends budget when it admits, so no slot is held; after 30 minutes the tick marks the request stuck for review, and the resource is admitted again |
| A later redrive | Applies nothing if a newer observation of the resource is already current |

## Why parsing and scheduling stay in Pronto

The alternative is a crawler that owns the complete request graph, application
callbacks and intermediate state, with only job acceptance and completion visible
to Pronto. The first updater took a variant of it: a Python coordinator with its own
PostgreSQL queue, leases and fencing, reaching the database through `psql` outside
Pronto's access rules and change processing. That duplicates the machines, moves
recovery and debugging into another runtime, and cannot run where the cluster has
no PostgreSQL connection.

The primary benefit of the chosen design is debugging through replay. Every
observation keeps its raw response, request and sequence number. When a parser
mishandles a score or a team name, reproduce the failure from that row, change the
function, and compare its output without contacting the source again. Promotion
into canonical facts still obeys ownership and review rules. Replay must not
redispatch follow-up requests.

Parsing in the database is synchronous because the commit that stores an answer is
the one that decides it. Responses are tens to hundreds of kilobytes of JSON;
parsing a round costs a small fraction of a function's fuel. Long or recomputing
derivations stay computations, which on the edge need their own Worker.

## Scheduling and the source budget

The SofaScore budget is six requests a minute shared by every source. `sofa.admit`
spends a slot in the same commit that creates the request, so concurrent
candidates cannot each consume the same final slot; every redirect hop beyond the
first is charged when its answer lands. Admission orders the due resources by
priority, result summaries before the inventory before details. Those are
decisions over every resource at once, and stay SQL.

What happens to one resource is its own: a Mecha reducer per resource
(`sofa_resource`), whose rules ([[../../machines/sofa_resource.js]]) are the first
updater's cadence: weekly beyond seven days from kickoff, daily within seven,
every four hours within one, at most every 20 minutes while a match may be live;
a daily inventory; one next-day check of a settled round or fixture; details
after an eligible new final, retried at 20 minutes, two hours, a day and a week,
then reviewed; a doubling backoff capped at 4 hours 16 minutes, and a detail
given up after five failures; and, after a championship ends, its rounds kept
until thirty days later and audited weekly while fixtures remain unresolved. A
waiting state's timer is XState's `after`, kept by the ticker and due `wait`
after the step that entered it, the time each action leaves until `due`, so no
rule reads a clock and the ticker alone decides the instant. The provider's standing
is a second reducer (`sofa_provider`) the admission consults.

A reducer per resource keeps each instance's context small and typed, as the caps
require, while the battery walks every transition and holds the invariants (a
given-up resource is a detail; a done or given-up one owes nothing; an acquiring
one leaves on its answer or failure); [[../../tests/sofascore-schedule.ts]] holds
the rules to `tools/sofascore/schedule.py`'s instants. Two alternatives were not
taken: a reducer per source, which would have carried hundreds of due instants in
one capped context; and due instants as columns the SQL reschedules, which leaves
the lifecycle without the battery's coverage. The request row machine keeps the
Airlock claim: claim, answer, failure.

Crawlee and Feldera were considered and rejected as schedulers. With Pronto as the
one authority for durable work ownership, Crawlee's queue would duplicate it and its
remaining role, per-worker pacing and concurrency, is the budget above. Feldera is
native and would need its own container to derive eligibility that a query
computes directly at this volume.

Retryable acquisition failure backs off; deterministic parse failure fails the
commit, stays with Airlock and applies once fixed, rather than refetching.

## Transport contract

The transport container serves one fixed profile: the upstream helper's wreq Chrome
149/macOS profile with its fixed request headers, built with a pinned Rust toolchain
and lockfile. `sofascore_fetch --listen ADDRESS` answers `POST /fetch` with the same
objects its JSON-lines mode reads and writes
([[../../tools/sofascore-fetch/README|the transport]]): a request names a path below
`/api/v1/`; the answer carries status, headers, final URL, each followed redirect,
the request count, elapsed time and a body bounded at 8 MiB while reading, or an
error. Unknown request fields are refused, so a caller cannot add a method, a header
or a cookie. The transport follows up to five redirects and refuses a sixth.

Every URL, the first and each redirect's, must be HTTPS on `www.sofascore.com`,
`sofascore.com` or `api.sofascore.com` under `/api/v1/`, with no port or credentials.
Those three public names are the destination policy, reached through DNS as the
provider publishes them; deployment egress restrictions carry any boundary beyond it.

Every hop is a request the provider counts. The source machine charges one budget
unit per request the answer reports, so a redirected fetch spends the budget it
actually used.

## Deployment boundaries

```cue
code: capabilities: hatches: sofascore: {
    kind: "container"
    note: "wreq Chrome TLS profile; one GET per call to allowlisted SofaScore hosts"
}
code: state: bridges: sofascore: {
    container: "sofascore"
    port:      8080
    simulator: {dockerfile: {…}, srcs: globs: ["simulators/sofascore/*"]}
}
code: state: effects: acquire: {
    sink: {bridge: "sofascore", idempotent: false}
    reentry: "repeat"
    note: "A repeated GET is harmless; observations are versioned by request"
}
```

See [[../../../../plugins/pronto/docs/container-bridges|container bridges]].

| Release model | Boundary |
| --- | --- |
| Local Compose | Bridges, Airlock, hybrids and plv8 exist; the bridge runs as its simulator, never the transport |
| `release@docker` appliance | Packages a smaller core stack without Airlock or the bridge |
| Kubernetes | Can host the image, but current release manifests do not package the complete required pipeline |
| GCP Cloud Run target | Its release engine rejects Airlock and clock services; GKE would follow the Kubernetes path |
| Cloudflare | Edge Airlock, hybrids and the clock exist; the bridge's container runs on Cloudflare Containers, owned by the airlock's dispatcher Worker |

On Cloudflare the container hatch runs on Cloudflare Containers and is reached
through its Durable Object binding, not a public origin: the effect's target is
the container, beside tsbifrost and a declared HTTPS origin. Functions run through `pgl_step` as hybrid
steps do. The transport is the only Golaberto component that needs a container
hatch: media uses R2, and mail uses the edge `email` binding described in
[[../../../../plugins/pronto/docs/edge-hatches|edge hatches]].

macOS ARM64 and Linux ARM64 native helper builds and live requests passed, and the
linux/amd64 image Cloudflare Containers runs builds and starts. Windows and x86_64
hosts, and a live request from the container on Cloudflare, need their own validation.

  SofaScore returns 403 with legacy and default headers.
- Native helper: the same events URL succeeds on macOS; round 1, lineups and
  incidents also succeed, emitting 26 events, two 23-player lineups and 24
  incidents.
- Compiler and cluster tests cover generic container bridges, custom ports, invalid
  references and absence of implicit database-network attachment.
- Thirty-two confinement/HTML tests cover both Cheerio versions, real legacy HTML and
  HTML-in-JSON fixtures, representative authority escapes and worker isolation.
- Seven upstream helper tests cover headers, allowed URLs, redirects, error previews
  and stalled response timeout on both tested OSes.
- Linux ARM64 container builds from a digest-pinned Rust image and fetches 26 live
  events.
- The first updater's tests and SQL regressions encoded the domain rules; a live
  Italy pilot imported round inventory, summaries, lineups and incidents. Its
  cadence tests are now SQL regressions of the due-time functions, its
  normalization and response checks recorded parity fixtures of the Jessie
  functions.
- `tests/sofascore.ts` covers admission under the budget, a late answer stored and
  never applied, a new fixture bound once, inventories owing their rounds, a final
  owing its details and the pair applying together, failures backing off, pausing
  and reviewing, enrollment, fixture seeding, stuck requests and identity recovery;
  `tests/sofascore-airlock.ts` runs requests end to end through the real Airlock and
  the simulator, redirects charged per hop.
- The `sofascore-fetch` check runs the transport's unit, HTTP and JSON-lines tests
  in its pinned image: allowlist, redirect cap, byte bounds and protocols.

Still to prove: a dead letter redriven after a fix (with bounded dead letters), the
destination policy on Cloudflare Containers, and canonical updates that do not
rewrite unchanged derived facts under live load.
